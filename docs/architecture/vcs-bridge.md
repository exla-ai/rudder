# Pinned jj working-copy bridge

Research/prototype checkpoint, 2026-10-30. Rudder baseline: `0c6e4d01c39c920d1e7bf3f0ee8f2418e0e10bbf` (4.0.0-alpha.4). Upstream jj: tag `v0.40.0`, commit `941d0290f5511db1d1cf8e4fe7365ba7d1828ea0`. Source inspected in a separate cache clone. A standalone, exact-pinned CLI/factory prototype now compiles and passes the controlled fixtures recorded below. That earlier prototype delegates filesystem work to `LocalWorkingCopy`. A separate feature-gated product crate and journal boundary now exist, described below; no default jj replacement or production VFS migration is enabled.

## Recommendation and actual extension seam

Build a narrow `rudder-jj` executable from **exactly pinned jj-cli and jj-lib 0.40.0**. Register `RudderWorkingCopyFactory` under a distinct type such as `rudder-cas-v1`, then retain jj's ordinary command dispatcher. This is a real jj CLI extension, rather than a command-output imitation. Put that executable on the managed attempt's PATH as `jj`; keep ordinary recoverable integration checkouts compatible with stock jj. A broad jj fork is unnecessary for factory registration.

The public builder is `jj_cli::cli_util::CliRunner::add_working_copy_factories(WorkingCopyFactories)`. Upstream includes a complete custom-working-copy example that registers a factory and adds a custom initialization command. Its initialization calls `Workspace::init_with_factories()` and supplies the chosen backend, signer, operation/index stores and working-copy factory. [CliRunner](https://github.com/jj-vcs/jj/blob/941d0290f5511db1d1cf8e4fe7365ba7d1828ea0/cli/src/cli_util.rs#L4184), [upstream example](https://github.com/jj-vcs/jj/blob/941d0290f5511db1d1cf8e4fe7365ba7d1828ea0/cli/examples/custom-working-copy/main.rs#L57).

The actual implementation surface is:

| Public API | Rudder responsibility |
| --- | --- |
| `WorkingCopyFactory::{init_working_copy,load_working_copy}` | Load a prebound attempt and small private state without enumerating the inherited source tree. Both methods are synchronous. |
| `WorkingCopy::{name,workspace_name,operation_id,tree,sparse_patterns,start_mutation}` | Report the current private jj state and acquire the attempt's working-copy lock. |
| `LockedWorkingCopy::{old_operation_id,old_tree,snapshot,check_out,reset,recover,set_sparse_patterns,rename_workspace,finish}` | Implement snapshot/materialization semantics and durable recovery, including changes made by ordinary jj commands. |

`WorkingCopy` and `LockedWorkingCopy` are `Any + Send`; the locked operations are asynchronous where filesystem/store work is required. `snapshot()` returns `(MergedTree, SnapshotStats)` and `check_out()` receives a real jj `Commit`. Merely wrapping `LocalWorkingCopy` and delegating these methods, as the demonstration does, **retains the local tree-walking cost**. [Traits and options](https://github.com/jj-vcs/jj/blob/941d0290f5511db1d1cf8e4fe7365ba7d1828ea0/lib/src/working_copy.rs#L50).

Use an explicit initialization entry point supplying the custom factory. Registering a factory does not make every stock `jj git init` choose it. jj persists the working-copy type under `.jj/working_copy/type`; stock jj fails with `UnsupportedType` when it cannot load that type. Never register Rudder's implementation as `local` and reinterpret existing local metadata. [Initialization](https://github.com/jj-vcs/jj/blob/941d0290f5511db1d1cf8e4fe7365ba7d1828ea0/lib/src/workspace.rs#L133), [type lookup](https://github.com/jj-vcs/jj/blob/941d0290f5511db1d1cf8e4fe7365ba7d1828ea0/lib/src/workspace.rs#L504).

Exact jj dependency boundary in the optional product bridge features:

```toml
jj-cli = { version = "=0.40.0", default-features = false, features = ["git"] }
jj-lib = { version = "=0.40.0", default-features = false, features = ["git"] }
```

Keep this in a separate native adapter package/process, away from the App render loop and engine's normal dependency graph. The compiled wrapper additionally pins async-trait 0.1.89 and clap 4.6.0; it requires no direct futures dependency. Its Cargo lockfile records transitive dependencies. Upstream declares Rust **1.89**, edition **2024**, and Apache-2.0. The prototype was compiled with rustc **1.99.1**; a Rust 1.89 build has not been run. Disabling the CLI's default features removes optional Watchman while retaining Git explicitly, confirmed by the compiled feature graph. [Workspace manifest](https://github.com/jj-vcs/jj/blob/941d0290f5511db1d1cf8e4fe7365ba7d1828ea0/Cargo.toml#L7), [CLI features](https://github.com/jj-vcs/jj/blob/941d0290f5511db1d1cf8e4fe7365ba7d1828ea0/cli/Cargo.toml#L134).

Upstream's supported minimum remains **Git 2.41.0**. That constant supplies unsupported-option guidance; it is not an unconditional startup version gate. The inspected fetch path invokes `git fetch --porcelain --prune --no-write-fetch-head`; `--porcelain` was introduced in Git 2.41. Real fixture commands with Git **2.39.5** passed local jj operations, real Git commit import/export and a push to a disposable local bare repository. Fetch from that same local repository failed with `Git does not recognize required option: porcelain` and the `git >= 2.41.0` guidance. Thus local successes do not establish full support for older Git, nor remove the requirement to qualify the Git executable selected on macOS. No global Git installation or provider remote was changed. [Minimum and error type](https://github.com/jj-vcs/jj/blob/941d0290f5511db1d1cf8e4fe7365ba7d1828ea0/lib/src/git_subprocess.rs#L44), [actual fetch arguments](https://github.com/jj-vcs/jj/blob/941d0290f5511db1d1cf8e4fe7365ba7d1828ea0/lib/src/git_subprocess.rs#L164), [unknown-option parsing](https://github.com/jj-vcs/jj/blob/941d0290f5511db1d1cf8e4fe7365ba7d1828ea0/lib/src/git_subprocess.rs#L389).

## Private metadata and reusable object seed

Every attempt gets private writable `.jj` and `.git` metadata on an ordinary private filesystem. Do not mount the engine's live `.jj`, CAS directory, journal, object credentials or writable shared refs into the guest. The guest can use a read-only **prepared VCS object seed**, separately created from authorized project history. That seed is an immutable artifact, not the engine's repository directory.

The seed should contain selected Git object closure/pack indexes plus the jj metadata needed to interpret those commits. It has an explicit manifest, version and retained lifetime. Each private Git object directory may use `objects/info/alternates` pointing at the guest's read-only seed mount. New objects, HEAD, refs, index, locks, configuration and all jj operation/view state stay private. No `jj workspace add` against a shared repository is needed at launch. Preparing/filtering history and generating the seed are amortized preparation work; a private CoW metadata view can then fork from that **sanitized private-repository template** without walking source files. On the inspected Fly ext4 host this means a separately qualified private OverlayFS metadata view, not assuming native reflinks; APFS can use its native clone path. These are helper-owned private mounts/clones, not host-namespace mounts over the engine repository. Persist a seed retention pin for every live attempt and recoverable metadata checkpoint: an alternates pathname or an opaque JSON reference alone is not a GC retention edge.

Bootstrap the private repository template once. Upstream initialization first creates an empty working-copy commit; do not expose a populated VFS root while the private jj state still claims the empty tree. Import the selected baseline, establish its working-copy commit and use the custom metadata-only reset/finish path to bind the already-prepared source tree. At per-attempt launch, remint only the attempt binding and relocation-sensitive metadata and verify that the inherited jj tree equals the prepared filesystem projection. Re-importing all history or discovering the initial tree from files on every launch would defeat the seed.

Use public `GitBackend::init_colocated` or `init_external` with a private Git repository, and `Workspace::init_with_factories` with the Rudder factory. Inspect/rewrite persisted repository locations when producing a relocatable template: `git_target` is a real path, and must never reference the engine's repository. [Git backend initializers and path storage](https://github.com/jj-vcs/jj/blob/941d0290f5511db1d1cf8e4fe7365ba7d1828ea0/lib/src/git_backend.rs#L231).

Preserve history rather than rebuilding an unrelated repository from a source tarball. jj 0.40 defaults `git.write-change-id-header = true`, but older history can depend on `.jj/repo/store/extra`. Git-only transfer can lose those legacy change identities. The public `stacked_table::{TableStore,TableSegment}` APIs can select metadata rows for authorized commit IDs into a private seed without inventing change IDs. This still depends on pinned backend layout/opaque row format and needs fixtures. `get_head()` can merge/write table heads: read from a trusted staged copy or under the project's VCS export lock, never treat it as an arbitrary read-only call. Returned guest metadata must be parsed/validated in quarantine rather than copied into the authoritative store unchecked. [Default setting](https://github.com/jj-vcs/jj/blob/941d0290f5511db1d1cf8e4fe7365ba7d1828ea0/lib/src/config/misc.toml#L12), [extra-metadata read](https://github.com/jj-vcs/jj/blob/941d0290f5511db1d1cf8e4fe7365ba7d1828ea0/lib/src/git_backend.rs#L1210), [table API](https://github.com/jj-vcs/jj/blob/941d0290f5511db1d1cf8e4fe7365ba7d1828ea0/lib/src/stacked_table.rs#L55).

Keep Git/jj metadata outside the current logical VFS mount. Its advertised unsupported operations include POSIX record locks. Private metadata bind mounts on ext4/APFS avoid making the VCS bridge depend on unqualified lock behavior. Configuration/hook/credential paths require deliberate sanitization; a copied engine config is not a safe metadata seed.

## Snapshot is not seal

A normal `jj status` loads the workspace through the CLI helper and snapshots it. Calling Rudder's terminal checkpoint here would stop the calling agent. Our current VFS rejects mounted/live checkpoints and requires closed handles; its `CheckpointConsistency` presently contains only `Quiesced`. A live working-copy observation must not be serialized as that authoritative source checkpoint. [jj status](https://github.com/jj-vcs/jj/blob/941d0290f5511db1d1cf8e4fe7365ba7d1828ea0/cli/src/commands/status.rs#L65), [current VFS checkpoint](../../engine/src/vfs.rs), [current consistency type](../../engine/src/protocol.rs).

The custom working copy needs a new per-attempt filesystem API returning **live dirty paths, generation/cursor and immutable byte versions** for a best-effort jj observation. It must detect cursor loss and concurrent checkout, and use an explicit fallback/rescan rather than silently return clean. Namespace transactions alone do not make mmap or open-handle bytes immutable. That data contract is additional VFS work, not supplied by the jj factory hook.

Maintain two boundaries:

1. Live/private jj history can reflect ordinary best-effort working-copy snapshots, as stock jj does while tools edit files.
2. A terminal filesystem seal produces the authoritative full recovery checkpoint. From it derive a separately identified **versioned source projection**, bind that projection to exact jj tree terms, and verify/integrate only that versioned root plus its declared environment.

Do not silently equate the full recovery tree with the Git/jj tree. Ignore rules, already-tracked files, auto/force tracking, sparse selection, maximum new-file size and prepared/scratch/VCS partitions all affect projection. A profile cannot silently remove tracked source under `node_modules` or another prepared path. Reject that incompatible profile or preserve the path as versioned source. Ignored local files may remain in recovery data, but authoritative verification must not depend on undeclared private leftovers. Existing source manifests must not silently change interpretation; introduce an explicit, versioned VCS projection/proof record.

The proposed private binding/proof boundary should include `project`, owner/run epochs, attempt ID, immutable VCS seed reference, authorized baseline commit/operation, filesystem view/generation and projection-policy identity. A sealed proof additionally binds the full recovery checkpoint, versioned source/environment references, exact jj commit/tree merge terms and labels, relevant decision versions and the intended integration base. Keep Git IDs, jj operation IDs and Rudder CAS references as different typed fields; do not fit them into one generic hash string.

The guest extension should request live VFS operations through an attempt-scoped broker; it never opens the host CAS/journal. `state_path` contains private jj state and broker identity references, not reusable engine credentials. Lock and compare old operation/tree plus filesystem generation on mutation. `finish()` persists the accepted generation and operation together with replay/recovery information.

`check_out`, `reset`, `recover` and sparse updates are real semantics. `jj edit`, `restore` and rebases must update only versioned source while retaining prepared dependencies, scratch and private VCS metadata. VFS root changes need defined open-FD/cwd behavior and crash recovery. An implementation supporting only `snapshot` cannot advertise ordinary jj compatibility. macOS can initially use a correctness-preserving local-WC fallback for status; APFS cloning alone does not provide a trusted live dirty cursor.

## Exact import, conflicts and publication

Rudder CAS identities are typed SHA256 records; jj's pinned Git backend uses Git object identities and serialization. They are not interchangeable formats. Convert blobs, executable modes, symlinks and directory trees explicitly, caching mappings for immutable subtrees. `Store::write_file/write_symlink/write_tree` and `MergedTreeBuilder::set_or_remove/write_tree` are public. Unchanged subtrees should reuse mappings, while changed hardlinked aliases must all project their visible bytes. Git/jj do not preserve hardlink identity, so keep that topology in the recovery checkpoint. jj 0.40 paths and symlink contents use UTF-8 strings; reject incompatible raw-byte names/targets explicitly rather than corrupting them. Also qualify case collisions on the actual macOS volume. [Store API](https://github.com/jj-vcs/jj/blob/941d0290f5511db1d1cf8e4fe7365ba7d1828ea0/lib/src/store.rs#L215), [merged tree builder](https://github.com/jj-vcs/jj/blob/941d0290f5511db1d1cf8e4fe7365ba7d1828ea0/lib/src/merged_tree_builder.rs#L39), [path representation](https://github.com/jj-vcs/jj/blob/941d0290f5511db1d1cf8e4fe7365ba7d1828ea0/lib/src/repo_path.rs#L42).

Preserve jj's first-class conflicts. Its Git representation uses special side/base trees for retention and `jj:trees`/conflict-label headers for interpretation. A materialized marker file is not the complete conflict. Reuse public conflict materialization and `conflicts::update_from_content` against the old merged value when interpreting edits. Export/import the full relevant commit/tree closure and metadata, not a flattened diff or only a marker-file tree. Test Git-authored commits, HEAD moves and rebases through real Git and jj; plain Git can discard jj headers or materialize the special conflict representation. [Conflict representation](https://github.com/jj-vcs/jj/blob/941d0290f5511db1d1cf8e4fe7365ba7d1828ea0/docs/git-compatibility.md#L227), [conflict update API](https://github.com/jj-vcs/jj/blob/941d0290f5511db1d1cf8e4fe7365ba7d1828ea0/lib/src/conflicts.rs#L1050).

On terminal seal, reconcile the private working-copy tree with the sealed versioned projection. Preserve agent-created commits and change identities. Any reconciliation commit/rewrite needs explicit lineage and immutable-history rules; it cannot rewrite canonical ancestors merely because guest metadata claims a change ID. Import new objects into host quarantine, verify bytes/closure and the projection-to-tree binding, and keep all prepared input/output roots retained through publication.

For integration, use jj's own transactions, commit builders, merges and descendant handling. `Transaction::write()` returns an `UnpublishedOperation`, and `publish()` later updates operation heads. That permits object/operation preparation before a short publication gate. [Staged operation API](https://github.com/jj-vcs/jj/blob/941d0290f5511db1d1cf8e4fe7365ba7d1828ea0/lib/src/transaction.rs#L134).

It does **not** atomically commit jj files and Rudder SQLite. Record a durable integration intent first; prepare objects without advancing visible heads; finally fence owner/run authority, actual integration head/operation, sealed source/environment and relevant decision versions. Serialize that final gate with competing integrations/decision acceptance while publishing the prepared operation, then record proof. A crash between publication and journal completion requires inspecting the exact operation/intent and reconciling uncertainty, not replaying a merge or globally restoring jj state. The existing `Journal::integrate()` validates and advances its own journal state; it does not perform this cross-store protocol. [Current integration gate](../../engine/src/journal/decisions.rs).

## Remaining cost and first fixture

A custom working copy does not remove all source-count work. In colocated mode `CliRunner` calls `git::reset_head()` during transaction finalization; `reset_index()` rebuilds an index from the parent tree and merges old index entries. This can still cost O(tracked files), even with delta snapshots. Measure it separately from file-content enumeration. Start with a private CoW index and cached Git objects; consider a narrowly upstreamable delta/index optimization only if it dominates. Dependency trees excluded from tracked source should never be traversed merely to launch an agent. [CLI finalization](https://github.com/jj-vcs/jj/blob/941d0290f5511db1d1cf8e4fe7365ba7d1828ea0/cli/src/cli_util.rs#L2227), [index reset](https://github.com/jj-vcs/jj/blob/941d0290f5511db1d1cf8e4fe7365ba7d1828ea0/lib/src/git.rs#L1712).

The standalone prototype below qualifies the API and selected history semantics. Before adding a production adapter, the remaining fixture should:

- Compile the exact registration surface and initialize/load a custom-type workspace. Stock jj must refuse that type; the extended binary must run ordinary commands without command shims.
- Fork 1/10 private attempts from one prepared VCS seed and source root. Instrument inherited file reads; launch/init must not walk source or dependencies. Record metadata/index bytes and history preparation separately.
- Run real `jj status/diff/new/describe/edit/restore/rebase` and `git status/diff/add/commit/checkout`, including ignored tracked files, executable bits and symlinks. Compare trees with a stock-jj reference.
- Preserve an unresolved conflict, edit its markers, partially resolve it and round-trip both current headers and legacy extra metadata. Verify change IDs, parents, labels and private operation history.
- Seal a dirty view, import its exact versioned projection and prove bidirectional byte/tree equality. Attempted stale owner/run/base/topic publication must fail without changing canonical history.
- Inject crashes before/after VFS checkout, private jj finish, unpublished operation creation, visible operation publication and journal completion. Retry must observe/reconcile the original intent rather than duplicate integration.
- Revoke an attempt, rotate identity and deny cross-attempt socket/path reuse. Verify that guest-visible mounts contain only its private metadata and the immutable VCS seed, with no engine journal/CAS/live `.jj` path.
- Run Linux and macOS compatibility separately; do not infer APFS case/lock/event semantics from Linux FUSE results. Keep UTF-8/type limitations explicit.

This is enough to decide whether the remaining work is a materializer and protocol implementation or one small upstream API change. The source does not justify replacing jj's history/conflict engine.

## Actual standalone prototype qualification

The reusable standalone prototype source, Cargo manifest/lockfile, Python fixture, raw report and provenance are preserved in the [source/evidence archive](../../examples/vcs/evidence/2026-10-30/README.md). This earlier prototype was built in a separate research cache and never launched against a user repository. It is distinct from the subsequently added product crate. The binary is a genuine `CliRunner` extension with the ordinary dispatcher, a `rudder-init` command and a distinct `rudder-prototype-local-v1` type. It does not impersonate the production `rudder-cas-v1` design. All 174 `jj-cli/src` files and 115 `jj-lib/src` files distributed in the resolved 0.40.0 crates match the inspected upstream commit byte for byte. Registry package checksums, source/lock/report hashes and compiler versions are preserved in `provenance.json`.

On the inspected Fly Linux host, the final six-test fixture passed **6/6 in 9.591 seconds**, using 82 real command invocations. Each test forked two independent private attempts from one prepared template. Initialization and fixture copying were eager preparation work, not a CoW or agent-launch benchmark. The prepared immutable Git object seed contained 4 files totaling 2,433 bytes; this is a semantic fixture, not a representative repository.

| Qualified behavior | Real observation |
| --- | --- |
| Registration and ordinary CLI | Stock jj rejects the custom working-copy type; the extension runs native `status`, `diff`, `new`, `describe`, `edit` and `restore`, with symlinks, executable modes and ignored dependency files. Trace events show actual local snapshot/checkout calls. |
| Private mutable metadata | Each attempt owns its `.jj` operation/view/workspace/extra state and `.git` refs/config/index/new objects. Mutating A leaves a complete fingerprint of B unchanged; B cannot read A's newly created commit object or ref. The relative `git_target` survives relocation. No `jj workspace add` is used. |
| Immutable object sharing | Attempts use Git object alternates pointing only to the prepared object seed. A new private user/mount namespace makes mount propagation private and binds that seed read-only. A test write returns `EROFS`; complete seed and template fingerprints remain unchanged. The namespace and its mount disappear when the fixture exits. |
| Conflict/history round-trip | A real two-parent unresolved merge exports to Git with `jj:trees`, conflict-label and change-ID headers. A fresh stock-jj repository imports only those Git objects, preserves the commit/change IDs and conflict state, and materializes byte-identical conflict markers/labels. Resolving the original markers preserves the change ID while changing the commit ID. |
| Legacy identity | Both private copies preserve a headerless legacy change ID through their private copied extra metadata. A separate fresh Git-only import deliberately obtains a different derived change ID, demonstrating why Git object sharing alone is insufficient. Selecting/filtering individual extra-table rows remains unimplemented. |
| Ordinary Git and version behavior | A real `git add`/`git commit` is imported by jj without losing the baseline's legacy identity. Local-bare push succeeds on Git 2.39.5; local-bare fetch fails on its unsupported `--porcelain` option. |

The namespace fixture does not create a restricted execution guest: it inherits the host filesystem before making mount propagation private. It mounts no engine `.jj`, journal, CAS, source cache or capability store, passes no provider credentials, and uses only disposable local Git remotes. These facts are not evidence of broker authorization or adversarial filesystem isolation. The non-Linux runner uses mode-only read-only files plus integrity checks and labels that weaker result; macOS execution has not been qualified.

Important remaining gates are unchanged: live dirty/versioned-byte observations; source-projection and exact sealed-tree import; scoped VFS broker operations; private CoW metadata forks without eager source enumeration; integration/decision/owner fences; crash reconciliation; metadata quarantine/filtering; index scaling; and macOS compatibility. `snapshot()` in this prototype still delegates to `LocalWorkingCopy` and can scan the source tree. Its successful native commands justify adopting the public extension seam, not declaring the production VCS bridge complete.

## Feature-gated product implementation

The [rudder-vcs-bridge crate](../../vcs-bridge/README.md) is a separate workspace member. Default features exclude jj and the CLI. Explicit `jj`/`cli` features use the exact upstream pins; `local-development` alone adds a delegated scanner type and `rudder-init-local`. No installed jj path, package-copy script or native launch default changes. The real `RudderWorkingCopyFactory` uses only an injected `WorkspaceView`; ordinary snapshots cannot silently fall back to LocalWorkingCopy.

The concrete boundary now includes:

- Typed raw Git commit/tree IDs, raw jj change/op IDs, ordered merged-tree terms and conflict labels, attempt/owner/run/view/profile/seed/policy bindings, namespaced live observation tokens and versioned sealed proofs. LiveBestEffort cannot be deserialized as a terminal seal. The actual VFS observation conversion preserves the request nonce, cursor namespace and separate exclusion digest; the provider still applies jj's complete projection semantics.
- A trusted private-metadata template, config/hook sanitization, retained CAS seed linkage, read-only object verification and fresh private attempt forks. Per-attempt history gets a new WC change ID on the exact authorized baseline, through jj-lib metadata operations with no source snapshot/checkout or shared `workspace add`. Copying private VCS metadata remains O(metadata files); per-host seed verification reads the selected VCS object seed once. APFS/OverlayFS optimization and cold-fleet scaling remain separate gates.
- Prepared immutable jj operations bound to an exact integration base and complete previous op-head set. Preparation preserves base ancestry and sets the engine-private `rudder-integration` bookmark to the intended commit. Inspect/publish never silently merge or rebase changed heads; record/op tags/commit/change/tree/proof identities must all match. Canonical user/main metadata is not the publication target.
- A [schema-4 journal intent boundary](../../engine/src/journal/vcs.rs): Accepted precedes preparation; inputs and prepared records are retained before publication; Started commits before the external effect; final owner/source-run-attempt/head/full-decision checks remain in the same IMMEDIATE transaction as the external update and integration receipt. Existing integration validation/apply helpers are shared. Legacy `integrate` cannot bypass Started/Uncertain publication or reuse a reserved VCS key. Older engines reject the newer schema.
- An actual trusted bridge-to-journal publisher adapter. A crash after effect but before receipt leaves Started/Uncertain. Reconciliation only inspects the same operation. A current owner can adopt a historical exact publication while immutable evidence/base/decision checks still match, despite retirement of the old source/owner. Published with changed gates remains Uncertain and blocks integration. A changed head is never treated as proof of no effect.

Actual stored Checkpoint/RunnableRoot source/environment and available view/profile/topology must match the intent. RunnableRoot additionally requires the actual schema-2 source/environment children and the exact SourceV2 policy. Existing checkpoint ancestry remains strong and unchanged. This first path requires the recovery root's source to be the versioned candidate itself; a differing source-subset derivation is rejected until a trusted projection receipt exists. The current common integration gate requires an explicit environment root, even though RunnableRoot can represent a launch without one.

The product Rust fixtures cover registered-provider dispatch, cursor invalidation, unsupported-before-start versus uncertain-after-start, exact private attempt identities, real jj publication, and a real jj/journal normal/lost-receipt path. Engine fixtures include a real subprocess exit after effect/before commit, source/version fences, historical receipt replay, stored recovery bindings and a decision writer serialized through physical publication plus receipt commit. The separate Linux RO fixture was actually run in a new user/mount namespace, with an `EROFS` witness and no provider snapshot/checkout calls. The product scanner CLI separately passed the six native command/history/conflict fixtures. These are semantic qualifications, not a fork/cache benchmark or macOS execution result.

The following source-projection checkpoint supersedes the empty-tree-only limit of that first fixture. Scoped live provider transport, mounted checkout and the native caller remain production gates. Pending external checkout has a durable nonce and refuses replay, but exact checkout reconciliation must be wired before enabling that capability. Published-with-changed-gates needs an explicit current-owner fresh-evidence adoption or compensating operation, never automatic acceptance of stale checks. Retention cleanup, untrusted metadata quarantine/filtering and real macOS qualification remain further gates. No full VCS bridge or v4 completion is claimed by this slice.

## Source projection checkpoint

The [immutable mapper](../../vcs-bridge/src/projection.rs) now reads actual Directory v1/v2 metadata and Blob/chunked File content. Normal files stream into the private Git object database using the public exact-pinned gix 0.81 API. The bridge avoids passing a fallible CAS reader to jj 0.40's Git `write_file`, whose implementation buffers the reader and unwraps its read error. Reverse preparation uses bounded Git blob reads and writes a new immutable CAS Directory under caller-owned staging. It does not replace a mounted root or write source files. [Pinned jj implementation](https://github.com/jj-vcs/jj/blob/941d0290f5511db1d1cf8e4fe7365ba7d1828ea0/lib/src/git_backend.rs#L1015), [metered I/O](../../vcs-bridge/src/projection_io.rs).

This first provider traverses the immutable source namespace and previous jj entries. It evaluates the actual current `SnapshotOptions`: base and nested ignore patterns, tracked files, auto/force tracking and new-file size. An owned prior record matching the exact prior jj tree/policy can reuse unchanged leaf values without rereading their content. It does not infer policy equality from opaque matcher/ignore Debug output or addresses, and it does not treat unchanged generation as an empty delta. A static policy hash identifies the projection program and exclusions, not every dynamic configuration object. Source-root or dirty-cursor loss requires the complete bounded traversal or an error. This is not an O(changes) namespace snapshot.

Regular file contents, executable bits, UTF-8 byte-preserving path names and UTF-8 symlink text round-trip. Source permissions beyond Git's executable bit, directory modes and hardlink topology stay in filesystem recovery state. File conflicts use pinned public jj materialize/update helpers, preserving merge terms, labels and the actual marker length across partial resolutions. A changed conflict without owned marker provenance must match the known materialization or fail; the bridge never guesses a shorter marker length and silently resolves it. The pinned Git backend itself currently reads placeholder copy IDs and ignores them when writing Git trees; this slice does not claim full copy-identity support beyond upstream. [Pinned copy-ID behavior](https://github.com/jj-vcs/jj/blob/941d0290f5511db1d1cf8e4fe7365ba7d1828ea0/lib/src/git_backend.rs#L1136).

Non-UTF-8 names/targets cannot be represented by pinned jj's path/target APIs and fail explicitly. ## Scoped RPC consumer and typed jj commands

[`RpcWorkspaceView`](../../vcs-bridge/src/rpc_view.rs) consumes the owning view's retained observation RPC. Only the host-side provider reads private CAS objects or jj metadata. It reuses the full mapper, dynamic tracking/ignore rules, conflict provenance and traversal budgets; it neither reopens a mounted namespace database nor walks a materialized source directory. A lost capture keeps its original pending UUID. Restarted consumers inspect that retained receipt and refuse a fresh capture until the uncommitted candidate is explicitly retired or reconciled. Captures remain `LiveBestEffort`.

`DurableWorkingCopyWitness` is constructed from protected host configuration. It verifies the exact attempt, retained source nonce, private projection/tree and durable WC state, loads the stated private jj operation and verifies its actual WC commit tree. It fsyncs the configured state and parent under a distinct publication lock held through RPC adoption and old-pin retirement. WC writers use that same publication lock for state replacement, then release it before calling adoption. The witness never reacquires the WC mutation lock already held by its caller; request-supplied paths, a tree hash or a peer's fsync claim grant no authority.

The [command service](../../vcs-bridge/src/command_transport.rs) accepts typed `status`, `diff`, bounded `log`, `new`, `describe` and same-tree `edit`. A guest proxy validates a strict grammar before connecting. It cannot forward arbitrary jj flags, aliases, configuration, templates, editors, Git transports, repository paths or host working directories. The host reconstructs fixed argv and configuration for the actual registered jj-cli dispatcher. Description strings remain literal values. Same-tree Edit uses one jj-lib observation and metadata transaction; it cannot run a hidden second snapshot or replace source inodes. A target requiring checkout fails before private history publication. Mounted checkout and sparse mutation remain Unsupported.

Command UUIDs and Started/Completed/Uncertain receipts are durable. A completed command whose reply is lost returns the same receipt after service restart; it does not create another `new` operation. Ambiguous Started commands are fenced as Uncertain and are not replayed. Full semantic reconciliation and a user-facing same-ID retry surface remain activation gates. A canonical inherited writer lock fences a still-live old CLI after service death. Production shutdown still needs to close ingress, await real handlers/children and hold that writer lock through finalization, rather than infer quiescence from a guest marker.

Five local RPC/CLI fixtures exercise nonempty projection and trusted adoption, original-capture and adoption reply loss, consumer/server restart, real default dispatcher commands, exact same-tree Edit, literal messages, denied configuration and stale attempts. These local fixtures use owning view handles and real Unix sockets, but do not themselves mount a kernel filesystem. The separate mounted qualification driver is [`qualify_mounted_rpc`](../../vcs-bridge/examples/qualify_mounted_rpc.rs); its Fly results and production activation limits are recorded separately.

## Explicit native v3 composition

[`workspace_vcs`](../../native/src/workspace_vcs.rs) now supplies the actual native broker authority and a protected host context. Execution v3 requires an explicit application specification; v1/v2 with application None retain their canonical bytes. The context's raw SHA256/size and private pathname are bound by the trusted sealed execution spec. Native requires canonical JSON, exact owner/run/attempt/view/namespace/profile/CAS/RPC bindings, private declared metadata/state roots, safe file ownership/modes/link counts and a pinned read-only runtime ELF. No credentials or context are placed in shared CAS or the guest. Unknown kinds, missing context and unsupported versions fail closed.

The engine remains independent of the bridge. A trusted generic application callback runs only after the owning workspace RPC is bound. It returns an explicit flat file/socket allowlist and host-owned environment under a fixed read-only `/run/rudder/services/<kind>` projection. Native prepares the nonempty private WC through the RPC provider, then exposes only the scoped command client. The native binary links bridge `jj`; the separately packaged `rudder-jj` companion alone links `jj-cli`. Default companion resolution uses only the current executable's sibling, with no stock-jj/scanner fallback; frozen qualification may provide an explicit pinned path.

Shutdown closes ingress under the actual child-spawn gate, settles handlers and owned child processes, then acquires the canonical writer fence. The engine retains that owned finalization guard through RPC settlement, strict unmount, retained checkpoint publication and execution-record fsync. Failed settlement leaves the view fenced and acknowledges no checkpoint. Stopped/timed-out commands remain Uncertain after possible private history effects; neither a peer's boolean nor output text can certify quiescence or authorize replay. Output readers have a bounded final tail, and child cancellation signals only an owned unreaped process/group.
