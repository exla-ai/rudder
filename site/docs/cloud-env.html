Match your cloud machine to your laptop

Your agents run on your cloud machine, not your laptop. Take every env file on your laptop, in the project and in your home directory, and put it on the cloud machine. Point your local agent at this page and it does it for you.

Hand this to your agent

Paste this into Claude Code, Codex or any coding agent running on your laptop, in the project you want to run in the cloud:

Read https://rudder.exla.ai/docs/cloud-env. Take every env
file this project uses and every one in my home directory
(~/.codex, ~/.claude and the rest) and put them on my Rudder
cloud machine. Follow the "Rules for agents" section.

The rest of this page is what the agent will do, and what you can do by hand.

Take every env file

Sign in once with rudder login, then run this in the project. It stores every env file git ignores, at the same path on the cloud machine:

repo=$(basename "$(git rev-parse --show-toplevel)")
cd "$(git rev-parse --show-toplevel)"
git ls-files --others --ignored --exclude-standard   | grep -E '(^|/)(.env[^/]*|.dev.vars|.envrc)$'   | grep -v node_modules   | while read -r f; do
      rudder cloud secrets set --file ~/code/"$repo/$f" "$f" < /dev/null
    done

Then the env files that live in your home directory, where Codex, Claude Code and other tools keep theirs:

for f in ~/.env ~/.codex/.env ~/.claude/.env ~/.config/opencode/.env ~/.npmrc ~/.netrc; do
  [ -f "$f" ] && rudder cloud secrets set --file "$f" "$f"
done
rudder cloud secrets sync

The last line brings over the agent logins and settings (Claude Code, Codex, git and GitHub). Run both again whenever an env file changes; a file stored twice is replaced. rudder cloud secrets list shows what is there, by name only.

Why it matters

A Rudder cloud machine starts with your repository and nothing that is not in git. Your .env files, API keys and tokens stay on your laptop, because git ignores them. An agent in the cloud that runs your tests or your dev server without them fails in ways that look like bugs in your code.

Rudder keeps these values in a vault on your account and hands them to your cloud machine. There is no API key to create and nothing to paste into a web page.

A project's environment is rarely one file. These are all the places to look, and how each one gets to the cloud machine.

The commands are below. Your agent runs through this table for you and shows you the list before it stores anything.

Sign the laptop in

npm install -g @exla/rudder
rudder login

rudder login prints a code and opens the browser. Approve it with the same account you use in the app. In the app this is Settings, then Sign in a computer. You do this once per laptop.

Single values

For a value that is in no file, only in your shell:

rudder cloud secrets set STRIPE_SECRET_KEY

It asks for the value without showing it. To set one from a script, pipe it in, so the value never lands in your shell history:

printf '%s' "$STRIPE_SECRET_KEY" | rudder cloud secrets set STRIPE_SECRET_KEY

Agents on your cloud machine get these as environment variables. An agent that is already running keeps the environment it started with; the next one you start has the new value.

Env files and other files

Most projects read a .env file rather than the process environment. Store the file itself, at the path it should have on the cloud machine:

rudder cloud secrets set --file ~/code/my-app/.env ./.env

The first path is where the file goes on the cloud machine, the second is the file on your laptop. Projects on the cloud machine live in ~/code/<repo name>, so ~/code/my-app/.env is the .env at the root of the my-app repository. A file in a subfolder works the same way: ~/code/my-app/apps/web/.env.local.

Any other file under your home directory works too, such as ~/.npmrc for a private registry. Files are capped at 1 MB each.

To bring over the agent logins and settings your laptop already has (Claude Code, Codex, git and GitHub) in one step:

rudder cloud secrets sync

Check it worked

rudder cloud secrets list

This lists names, kinds and sizes. It never shows a value. Then ask an agent on the cloud machine to confirm what it sees, by name only:

Check that these env names are set, without printing their values:
STRIPE_SECRET_KEY, DATABASE_URL. Then run the test suite.

The cloud machine picks up vault changes when it wakes and when you open or add a project. If a new agent does not see a value you just set, open the project in the app and start the agent again.

To remove something: rudder cloud secrets rm NAME, or rudder cloud secrets rm ~/code/my-app/.env for a file.

what the vault does not carry

Only values and files. Tools your project needs, such as a database, a language version or a CLI, are installed on the cloud machine by asking an agent there to set the project up. The cloud machine is Linux, so a macOS-only tool needs its Linux equivalent.

Rules for agents

If you are an agent doing this for someone, work through these in order. Never put a value on a command line, in a file you commit, in a chat message or in your summary. Names and paths only.

  1. Run rudder --version. If it is missing, install it with npm install -g @exla/rudder. Never run a bare rudder <word> that is not a listed command; it starts a paid agent.
  2. Run rudder cloud secrets list. If it says you are not signed in, ask the person to run rudder login and approve it. Do not try to sign in for them. Keep the list: it is what the cloud machine already has.
  3. List every ignored env file in the repository, in the root and in each package, with git ls-files --others --ignored --exclude-standard. Skip dependencies and build output.
  4. List every env name the code reads. Search the source for the language's env calls, and read .env.example, docker-compose.yml, the Dockerfile, package.json scripts and the CI workflows. This is the full set of names the project can use.
  5. For each name, find where its value comes from on this machine: an env file from step 3, the shell (profile exports or .envrc), or a tool that pulls it (vercel env pull, doppler, op). Check whether a name is set with a test that prints yes or no, never the value.
  6. List the home directory config the project's tools use, from the table in Everything a project can read, and any key file an env value points at.
  7. Show the person one table before storing anything: each env file and its path, each name and where its value comes from, each home file, and each name with no value anywhere. Mark what points at the laptop only, such as a localhost database URL or a macOS path, and ask whether the cloud machine runs that service too. Wait for a yes.
  8. Store every file in one pass with the two loops under Take every env file: each repository env file at ~/code/<repo name>/<path in repo> (the repo name is the last part of the git remote, the name the project has in the Rudder app), each home file at the same path under ~, then rudder cloud secrets sync.
  9. Store values that are only in the shell by piping them in, as shown under Single values. For values a tool pulls, pull them into an env file on the laptop and store that file.
  10. Run rudder cloud secrets list again and compare it with the table. Report the files and names stored, the names that still have no value, and anything left out and why. Then give the person the check prompt from Check it worked, with the project's own names filled in, to run on the cloud machine.
